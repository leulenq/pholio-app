## 2. Multimodal / image embeddings for fashion & portraits

**Can they match abstract casting language to photos?** The clearest direct evidence is a fashion-specific benchmark called **LookBench** (found via search as arXiv 2601.14706, dated Jan 2026 — recent enough I could not deeply verify beyond the search summary): it explicitly reports that **generic backbones like CLIP and SigLIP2 underperform on real-world fashion "look" categories, particularly a "RealStreetLook" subset** — i.e., stylistic/vibe-level matching is harder for these models than literal object/product matching. On that benchmark, SigLIP2-B/16 scored 59.44 overall vs. CLIP-L/14's 39.79 — a large gap, but both are well below what you'd want for production trust.

**Fashion fine-tuning result:** Marqo's own published numbers (via HuggingFace/GitHub) claim **+22% recall@1 (FashionCLIP) and +57% recall@1 (FashionSigLIP)** over FashionCLIP 2.0, averaged across 7 public fashion benchmark datasets covering text-to-image, category-to-product, and subcategory-to-product retrieval. **Caveat that matters a lot for Pholio:** those benchmarks are *e-commerce product* retrieval (garments, categories, colors, materials) — not *person/casting* retrieval (androgynous, commercial warmth, bone structure, girl-next-door). Treat the Marqo fashion-tuning gains as evidence the *technique* (domain fine-tuning) works, not as proof it transfers to Pholio's exact vocabulary.

I could not find a directly-sourced images/sec CPU benchmark number for it, so treat this as a reasoned estimate from general ViT-B/16 ONNX CPU performance (not independently sourced): roughly 100–400ms/image single-threaded, meaning a batch of a few thousand images (Pholio's whole photo corpus today) completes in minutes to low tens of minutes on ordinary CPU, trivially parallelizable across images. This is compute time on a worker you run yourself, not an API bill — but note Netlify Functions are not a good place to run this (no GPU, execution-time limits); it wants a small always-on worker or a scheduled batch job (Modal, fal, a cheap VM, or even a GitHub Actions runner for a one-off backfill).

## 3. VLM captioning as an alternative to raw image vectors

**General-purpose evidence (not casting-specific) leans toward direct multimodal embedding beating caption-then-embed** for literal visual retrieval: one 2025 paper comparing text-based (caption/summarize-then-embed) vs. image-based (native multimodal embedding) retrieval in RAG pipelines found direct embedding ahead by **+13% abs mAP@5 / +11% abs nDCG@5 (≈32%/20% relative)**, with the caveat that in zero-shot regimes with smaller LLMs, captioning could actually be better, and the few-shot case depended heavily on in-context example selection. That study's domain looks like general documents/screenshots, not fashion or people photography — **the transfer to Pholio's abstract-style casting queries is genuinely uncertain, not settled by this evidence.**

**Why captioning may still be the pragmatic choice for Pholio specifically, despite that general finding:** text embedding models are trained on vastly more and richer *language-to-language* contrastive pairs than image-text contrastive models are on *abstract stylistic adjectives* (most image-text training data is literal/descriptive — product listings, alt-text — not "editorial," "commercial warmth," "girl-next-door"). A VLM that explicitly writes out shot type / styling register / mood / lighting / wardrobe / setting / expression in words, then handing that to a strong text embedder, routes the hard "does this look editorial?" judgment through the VLM's world knowledge (which has seen fashion/photography criticism, magazine copy, casting-adjacent language in its pretraining) rather than asking a contrastive image encoder to have learned that concept axis directly. **This is a hypothesis Pholio should A/B test on its own golden-brief set (§6), not something the literature settles either way.**

## 5. Retrieval architecture on Neon Postgres

**pgvector capabilities relevant here** (from the pgvector project itself and Neon's docs):
- **HNSW index** — available since pgvector 0.5.0, standard ANN index for cosine/L2/inner-product.
- **halfvec** (0.7.0) — 16-bit float storage, halves memory/storage and speeds index builds "without compromising recall" per one source; a good default at 50k-profile scale.
- **Binary quantization** — reduces each dimension to 1 bit (32× compression for a 1536-dim OpenAI vector), large recall trade-off, generally used with an overfetch + rerank step to recover accuracy rather than as the sole ranking signal.
- **Iterative index scans** (0.8.0) — automatically re-scans the HNSW index when a filtered query (e.g., height ≥ 5'9", market = New York) discards too many ANN neighbors before the vector similarity gets a fair chance. **This directly matches Pholio's query shape** — hard deterministic filters (already extracted by the LLM constraint step) combined with soft vector similarity — so upgrading to a pgvector version with iterative scans matters more for Pholio than it would for a pure-vector-search app.
- **Neon:** pgvector ships on every Neon plan at no extra cost, with Neon typically tracking "the latest supported version, one behind" per its own docs — I could **not** confirm the exact pinned version number from search results; verify directly against the live Neon project (`SELECT * FROM pg_available_extension_versions WHERE name='vector';`) before assuming 0.8.x is available.

**Hybrid search (pgvector + tsvector + RRF):** the standard pattern is two independent queries — one ANN vector search, one native Postgres full-text search (GIN index on `tsvector`) — merged with Reciprocal Rank Fusion (`score = Σ 1/(k + rank)`, k=60 is the common default), avoiding any need to normalize cosine distance against `ts_rank_cd` on a shared scale. This replaces Pholio's current "deterministic matching + lexical tie-break" with a principled fusion of lexical and semantic signal, in a single SQL query, no new infrastructure. One blog's own numbers (not an academic benchmark — treat as anecdotal) reported pure-vector retrieval precision around ~62% vs. ~84% after adding full-text + RRF, illustrating why hybrid beats vector-only especially for exact terms (agency names, specific lane/specialty vocabulary) that embeddings alone can blur.

**Per-chunk multi-vector vs. one-vector-per-profile:** pgvector does **not** natively support ColBERT-style multi-vector/late-interaction search (there's an open GitHub feature request, #694, still unresolved) — true max-sim scoring would require either computing it in application code (fetch candidate vectors, score in-process) or an external engine built for it. Voyage's **voyage-context-4** sidesteps this: it produces contextualized *chunk*-level vectors (one per chunk, context baked in) rather than per-token vectors, so it stays fully pgvector-compatible while still getting most of the benefit of context-aware chunking. **Recommendation for Pholio:** don't chase true multi-vector/late-interaction infrastructure at this scale — a small fixed number of vectors per profile (e.g., one for bio+lanes text, one pooled/averaged or a couple of representative photo-caption vectors) is simpler, cheaper, and plenty for hundreds-to-50k profiles; revisit only if the eval harness (§6) shows real recall loss from pooling.

**Does an external vector DB buy anything at 50k profiles?** At 50k profiles × a handful of vectors each (say 1 text + up to 4–5 photo-caption vectors), you're looking at roughly 250k–300k vectors of 1536 dims (or ~768 bytes each as halfvec) — well inside the range where pgvector/HNSW on ordinary Postgres hardware performs well; dedicated vector databases (Pinecone/Weaviate/Qdrant/Turbopuffer) generally start earning their keep in the 1M–10M+ vector range, or when you need very aggressive p99 latency at high QPS, or massive real-time upsert throughput — none of which describes an internal agency search tool at 50k profiles. **My assessment is that pgvector on Neon should comfortably suffice through 50k profiles; this is reasoned synthesis from general pgvector performance characteristics gathered above, not a single source stating this exact number for Pholio's case** — worth a load test before fully committing, but not worth pre-emptively adopting a second database for.

**Serverless concerns:**
- **Cold start:** Neon's own materials cite cold starts in the ~300–500ms range historically, with some claims of sub-200ms more recently; mitigate via Neon's pooled connection string (PgBouncer) so only the very first request in a while pays the cold-start cost, and consider Neon's autoscaling/min-compute settings for the Discover feature specifically if agencies expect snappy search.
- **Embedding-call latency budget:** query embedding call ~100–400ms (OpenAI/Voyage/Cohere), pgvector ANN scan ~10–50ms with a warm connection and proper index, reranker call ~150–650ms (per §4 numbers), hybrid RRF merge negligible (single SQL query). **Realistic end-to-end Discover search latency: ~500ms–1.5s.** That's fine for an agency search UI, not something to chase toward sub-100ms.
- **Caching query embeddings:** cache the embedding vector (and/or the LLM's extracted structured constraints) keyed by a hash of the normalized brief text, in a Neon table or an external KV (Netlify doesn't ship Redis natively; Upstash is a common serverless-friendly choice) to skip re-embedding repeated or near-identical briefs. Low priority at hundreds of profiles/searches; worth doing once search volume grows meaningfully.

## 6. Evaluation

**Golden briefs + nDCG@10 is the right small-corpus method.** Standard IR evaluation practice applies directly: assemble ~20–50 realistic casting briefs (ideally pulled from real agency usage or booker interviews), hand-label which talent in the corpus are relevant to each, and compute nDCG@10 (matches how a booker actually scans results — top-of-list quality, not full-corpus recall). This is cheap to build and re-run after every pipeline change, which matters given how many open questions this report surfaces (caption-vs-direct-embedding, model choice, chunking strategy).

**LLM-as-judge is a validated technique for scaling up relevance labels**, provided it's checked against real human judgment first. The pattern found across multiple sources: give the judge a query + candidate document (here: brief + talent profile/photos) and a relevance rubric, and treat its label as an approximation of a human rater's; nDCG@10 computed over LLM-judge labels has been shown to correlate well with human-evaluated rankings in at least one cited comparison. The guidance found for trusting a judge at scale is **75–90% agreement with human labels** on a held-out sample before relying on it broadly. For Pholio: use a cheap-but-capable judge (GPT-5-mini or a Groq model) with a rubric that focuses purely on the *aesthetic/style* match, since hard constraints (age, height, location) are already handled deterministically upstream and shouldn't be re-litigated by the judge.

**Click/invite feedback** (agency views a profile, shortlists, or messages/invites talent from search results) is the standard "implicit relevance signal" pattern in production IR — genuinely useful once there's real usage volume for tuning the blend weights between vector score / lexical score / rerank score, but Pholio likely won't have enough search-log volume to make this statistically meaningful until well into the "low thousands of profiles" stage or beyond, given it's an internal agency tool rather than a high-traffic consumer search product.

**Fairness — this is the section with the most legal/reputational weight for Pholio and the most concrete published evidence:**
- CLIP exhibits measurable gender skew even on gender-neutral queries: one cited MS-COCO study found gender-neutral text queries returned male-depicted images ~64% of the time.
- CLIP has been shown to associate Arab-Muslim- and African-American-appearing faces with negative/unpleasant concepts in some evaluations.
- A 2025/2026-era paper on debiasing found that **"intrinsic bias is largely predictable from pretraining data, not architecture"** — meaning swapping CLIP for SigLIP2 or a fine-tuned fashion model does not, by itself, fix this; the bias tracks what the model was trained on. The same source found "bias prompt" mitigations helped on smaller ViT-B/32 but became unstable — sometimes worse — at larger ViT-L/14 scale.
- Multiple 2025 audits (LAION-400M person-centric annotation study, multilingual CLIP gender/race disparity study, and a broader "auditing social bias in contrastive VLMs" paper) document that the issue is well-established and not fully solved by any single published mitigation.

**Practical mitigations found in the literature, mapped to Pholio's architecture:**
- **Fair sampling / balanced contrastive training** — only relevant if Pholio ever fine-tunes its own image encoder; not applicable to the caption-then-embed approach.
- **Post-hoc feature-clipping / projection debiasing** — an information-theoretic technique to strip protected-attribute signal from embeddings after the fact; feasible to layer on top of any off-the-shelf embedding, worth evaluating if an audit surfaces skew.
- **Attribute-neutral captions** — directly actionable for Pholio's likely architecture (§3): write the VLM captioning prompt to describe styling, mood, lighting, wardrobe, setting, and expression, and explicitly instruct it *not* to describe or infer race, ethnicity, or gender presentation. Since the abstract style queries ("editorial," "commercial warmth") would then be matched against text that structurally never encodes protected-attribute language, this meaningfully reduces (though doesn't provably eliminate — biased *associations*, e.g. certain styling registers correlating with skin tone in the training data, can persist) the risk that "clean beauty" or "girl-next-door" become a proxy ranking signal for race or body type.
- **Query-time auditing** — periodically run the golden-brief set (or a dedicated "style-only, demographics-blind" battery) and log/review the demographic distribution of top-K results across Pholio's real talent pool, to catch skew empirically rather than relying only on model-level assurances. Given this is an *agency* tool making real casting-adjacent decisions, I'd treat this as a standing operational process, not a one-time launch check.

## Recommendations

### (a) Today — hundreds of profiles

**Keep the current OpenAI embedding investment; add captioning, hybrid retrieval, and a cheap reranker. Don't add a second database.**

1. **Text embeddings:** keep `text-embedding-3-small` (1536-dim, $0.02/1M) for bios/lanes/specialties — no reason to migrate at this corpus size; the model-quality delta versus Voyage/Cohere/Google is second-order at hundreds of profiles.
2. **Photo → text bridge:** add a VLM captioning step to the existing async image pipeline (alongside Sharp processing). Use **Groq Llama 4 Scout** (already integrated, vision-capable, ~$0.13/M blended) or **GPT-5-mini** (~$0.0005/image) with a constrained prompt covering shot type, styling register, mood, lighting, wardrobe, setting, expression — **explicitly instructed to avoid describing/inferring race or gender presentation** (fairness mitigation from §6). Embed captions with the same text-embedding-3-small model; store 1 vector per photo, or pool the top 3–5 photos per profile plus 1 bio vector.
3. **Storage/index:** plain `vector(1536)` columns in Postgres. At this scale (well under 10k rows) **skip HNSW entirely** — brute-force `ORDER BY embedding <=> query_vec LIMIT 50` is fast enough and avoids index-tuning work.
4. **Retrieval:** replace the current "deterministic match + lexical tie-break" with **vector search + existing tsvector full-text, merged via RRF** — one SQL query, no new infra.
5. **Reranking:** either skip a paid reranker and do a single cheap Groq LLM call to re-rank the top 20–30 hybrid candidates, or use **Cohere Rerank 4 Fast** (~$0.002/search) — trivial either way at hundreds of searches/month.
6. **Eval:** build the 20–50 golden-brief set now (§6), before scaling anything — it's the only reliable way to know whether caption-then-embed is actually working on Pholio's real vocabulary.

**Estimated cost per 1,000 profiles indexed** (≈15 photos + 1 bio each): captioning ≈ $1–8 depending on vendor (Groq cheapest, GPT-5-mini moderate) + embedding (≈1.9M tokens × $0.02/1M) ≈ $0.04 → **roughly $2–10 per 1,000 profiles total.**
**Estimated cost per 1,000 searches:** query embedding negligible + reranker ≈ $0–2 (free self-rerank vs. Cohere) → **roughly $0–2 per 1,000 searches.**
**Estimated latency:** ~500ms–1.2s end-to-end (embed query + brute-force scan + rerank + merge).

### (b) A few years out — ~50k profiles

**Same core pipeline, hardened for scale — still no external vector database on current evidence.**

1. **Index:** move photo/bio vectors to **halfvec + HNSW**, and make sure whatever pgvector version Neon has pinned includes **iterative index scans (0.8+)** — verify this directly against the live Neon project, since I could not confirm the exact pinned version from search. This matters specifically because Pholio's queries combine hard filters (height, market) with soft vector similarity, which is exactly the case iterative scans were built for.
2. **Model re-evaluation (not pre-emptive migration):** before committing further budget, run **voyage-4** and/or **Cohere embed v4** (with proper query/document `input_type` asymmetry) against the existing OpenAI pipeline on the golden-brief eval harness. Only migrate if it measurably moves nDCG@10 — a full re-embed of 50k profiles + ~750k photo captions is a one-time but non-trivial job, budget for it explicitly if you do it.
3. **Consider a real image-embedding channel as a second signal** (Marqo-FashionSigLIP or SigLIP2, self-hosted on Modal/fal — not Netlify Functions, which can't run this workload) *only if* the eval harness shows the caption-only pipeline is missing recall on genuinely visual-but-hard-to-caption traits. Don't add this speculatively.
4. **External vector DB:** at ~50k profiles × a handful of vectors each (≈250k–300k vectors), pgvector/HNSW on Neon should still comfortably handle this — dedicated vector databases generally justify themselves past roughly 1M+ vectors or under very aggressive latency/QPS SLAs, neither of which describes an internal agency tool at this scale. Load-test before ruling it out entirely, but don't pre-adopt one.
5. **Reranker:** keep a paid reranker (Cohere Rerank 4 Fast or Voyage rerank-2.5-lite) on top-50–100 candidates; cost stays trivial per search even at real volume.
6. **Caching:** start caching query embeddings (and/or the LLM's extracted constraints) for repeated/near-duplicate briefs — worth the small implementation cost once search volume is meaningful.

**Estimated cost per 1,000 profiles indexed:** text pipeline (captioning + embedding) stays roughly **$2–10 per 1,000 profiles** (linear per-token pricing doesn't change with corpus size); add **~$3–15 per 1,000 profiles** if a paid image-embedding API is layered in (Cohere/Voyage image pricing), or near-zero marginal $ (just compute) if self-hosted.
**Estimated cost per 1,000 searches:** stays in the same **$0–5** range with a paid reranker; caching reduces this further as query repetition increases.
**Estimated latency:** HNSW keeps the ANN scan under ~50ms even at 250k–1M vectors, so end-to-end latency should stay in the same **~500ms–1.5s** band, now bottlenecked by the embedding/reranker API round-trips rather than the database.

## Honesty about uncertainty — read before budgeting

- **Pricing was mostly gathered via third-party aggregators** (embeddingcost.com, tokenmix.ai, pecollective.com, OpenRouter, CloudPrice), not primary vendor pages, except OpenAI's pricing page which was fetched directly. **Re-verify every number against the vendor's own current pricing page before committing budget** — these change frequently and aggregators can lag or misparse.
- **MTEB/BEIR scores are point-in-time snapshots** that shift as models and the benchmarks themselves are updated; treat relative rankings between models as more trustworthy than exact score values, and expect some of these numbers to already be stale by the time this is read.
- **No benchmark exists for casting-specific abstract vocabulary.** Every retrieval-quality number in this report is either generic MTEB/BEIR (broad-domain text retrieval) or fashion e-commerce retrieval (product attributes) — neither is a verified proxy for "does this photo read as editorial with commercial warmth." Pholio's own golden-brief evaluation (§6) is the only way to actually resolve this, and should be built before finalizing any model choice.
- **Several fashion/casting-adjacent papers cited (LookBench, and other very-recent-dated arXiv entries) came from search-result summaries only** — I did not do a full close read of the underlying PDFs, so their exact methodology and number precision should be treated as indicative rather than verified; read the primary source before citing internally in a way that matters.
- **Reranker "beats competitor X by Y%" claims are self-reported by the vendor's own blog** (Voyage vs. Cohere/Qwen, ZeroEntropy vs. Jina) — directionally useful for shortlisting, not independently audited.
- **Casting-platform "AI matching" claims (§7) are sourced almost entirely from marketing/comparison content**, including from platforms competing against the ones being described. I found **no primary technical disclosure** from Casting Networks, Backstage, Models.com, Storm, Snapcast, or Zodel about their actual algorithms. The "reference-image lookalike search" precedent question came back essentially empty, but my search depth there was shallow — treat "not found" as inconclusive, not as confirmation nobody does this.
- **Neon's exact currently-pinned pgvector version was not confirmed** from search results — verify directly against the live database before assuming 0.8.x features (iterative scans) are available.
- **Cohere embed v4's exact image-tokens-per-photo figure was not found**, so the per-image dollar cost for that specific vendor is an open question — Voyage published a direct per-image cost formula and Cohere did not; test empirically or ask Cohere directly before relying on it for budgeting.
